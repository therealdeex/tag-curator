# Stash v0.31.x: Channels for plugin-UI to receive rich output from a raw-interface Python task

All source claims below were verified by cloning `stashapp/stash` at tag **v0.31.1** and reading the actual schema and Go/UI source, cross-checked against docs.stashapp.cc. GitHub blob URLs are pinned to the `v0.31.1` tag.

## TL;DR

The stdout JSON envelope of a raw plugin **never reaches GraphQL directly** — for `runPluginTask` jobs it is only logged server-side at Debug level. But v0.31.1 has four real channels: (1) `runPluginOperation` returns the stdout envelope's `output` field **directly in the mutation response** (added in v0.25.0, PR #4603); (2) `jobsSubscribe` pushes `Job.progress` updates in real time, driven by stderr progress frames `\x01p\x02<float>`; (3) `loggingSubscribe` streams plugin stderr lines (info/warn/error) to the browser; (4) `configurePlugin` is an officially sanctioned read/write key-value side channel. The snapshot-assets approach you have today is a legitimate community pattern (Mosaic Poster uses it) but has no push, has HTTP-cache staleness risk, and needs atomic writes.

---

## 1. `findJob` / `Job` type — no output, but progress IS live

**Schema (v0.31.1)** — [`graphql/schema/types/job.graphql`](https://github.com/stashapp/stash/blob/v0.31.1/graphql/schema/types/job.graphql):
```graphql
type Job {
  id: ID!  status: JobStatus!  subTasks: [String!]  description: String!
  progress: Float  startTime: Time  endTime: Time  addTime: Time!  error: String
}
```
There is **no output/log field** on `Job`. Details:

- **stdout envelope is discarded for job tasks.** [`pkg/plugin/raw.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/plugin/raw.go) does `io.ReadAll(stdout)` — the whole stdout is buffered until process exit, parsed into `PluginOutput{Output, Error}`, and stored only in the in-memory task result. In [`internal/manager/task_plugin.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/manager/task_plugin.go) that result is merely logged: errors at `logger.Errorf("Plugin returned error: %s", ...)`, success at `logger.Debugf("Plugin returned: %v", ...)`. It is not queryable.
- **`Job.error` does not carry plugin errors.** It is set only when the job-exec function itself returns an error (task creation/start failure) — [`pkg/job/job.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/job/job.go) `j.error(err)`; the plugin's own `PluginOutput.Error` never propagates there.
- **`description` is static** ("Running plugin task: <desc>"); `subTasks` (`Job.Details`) is only settable from Go via `Progress.ExecuteTask` — a raw plugin cannot write it.
- **`progress` (0–1 float) IS plugin-settable and pushed live.** Stderr frames with the progress level flow: [`pkg/logger/plugin.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/logger/plugin.go) `ProgressLevel` → `ProgressChan` → `progress.SetPercent` → `updateProgress` ([`pkg/job/manager.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/job/manager.go)), which notifies `jobsSubscribe` subscribers, **throttled to 100 ms** (`defaultThrottleLimit`). Format: `\x01p\x020.42\n` to stderr (control chars `\x01`/`\x02`, level char `p`).
- **`jobsSubscribe: JobStatusUpdate!`** ([schema.graphql](https://github.com/stashapp/stash/blob/v0.31.1/graphql/schema/schema.graphql), resolver [`internal/api/resolver_subscription_job.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/resolver_subscription_job.go)) pushes ADD/UPDATE/REMOVE over the GraphQL WebSocket. This is exactly what Stash's own UI does: [`ui/v2.5/src/utils/job.ts`](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/utils/job.ts) `useMonitorJob` = `useJobsSubscribeSubscription` + `useFindJobQuery` (fetchPolicy `network-only`, 1 s polling fallback when WS is down). Both hooks are exposed to plugin JS via `PluginApi.GQL` ([`pluginApi.d.ts`](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/pluginApi.d.ts) lines 368/462).

**Feasibility:** progress bar = first-class; anything textual = no.
**Latency:** ~100 ms server-side throttle; true push via WS.
**Caveats:** only a bare float — no phase names, counts, or scene titles; finished jobs are removed from the queue (kept in a 10-entry graveyard, `maxGraveyardSize`), and a REMOVE event carries the final state.

## 2. `/logs` query + `loggingSubscribe` subscription

- The query is named **`logs`** and the subscription **`loggingSubscribe`** (not `logsSubscribe`) in v0.31.1 ([schema.graphql](https://github.com/stashapp/stash/blob/v0.31.1/graphql/schema/schema.graphql) lines 144/603). `LogEntry { time, level, message }` — **no job ID**, so filtering must be by message prefix.
- **Plugin stderr does land in these logs, line-by-line.** [`pkg/plugin/log.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/plugin/log.go) + [`pkg/logger/plugin.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/logger/plugin.go): every stderr line is scanned; if it starts with `\x01<t|d|i|w|e>\x02` it is emitted at that level, otherwise at the yml `errLog` level (**default Error**). Messages appear as `[Plugin / <name>] <message>` — a reliable filter key. Docs: [External Plugins — Logging](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/docs/en/Manual/ExternalPlugins.md) (mirrored at docs.stashapp.cc/in-app-manual/plugins/).
- **Progress frames are NOT logged** — `\x01p\x02...` goes only to `Job.progress`.
- **`/logs` query is nearly useless**: [`internal/log/logger.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/log/logger.go) `addToCache` keeps only the **last 30 entries** and only those at/above the server's configured log level (default Info).
- **`loggingSubscribe` is usable**: resolver [`internal/api/resolver_subscription_logging.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/resolver_subscription_logging.go) streams batches. Caveats (from `broadcastLogItem`): batches are coalesced and sent **at most once per second**; a full subscriber buffer (100) silently drops batches. Exposed to plugin JS as `PluginApi.GQL.useLoggingSubscribeSubscription`.
- **The final stdout envelope**: logged only at **Debug** level. Subtlety verified in code: `addToCache` level-filters but `broadcastLogItem` is unconditional — so the "Plugin returned: ..." Debug line *is* broadcast to `loggingSubscribe` subscribers even at default Info level, but does *not* appear in the `/logs` query unless the server log level is Debug/Trace. Relying on this is fragile (it's a one-line final blob, and level behavior could change).
- Bonus: your "progress frames to stderr today" are likely being swallowed (if unprefixed, they land at `errLog` level as errors; if `\x01p\x02`-prefixed, they become Job.progress, not logs).

**Feasibility:** good for human-readable status lines ("phase 2/5", "8,412/20,595 scenes", "current scene: X").
**Latency:** ≤1 s batching.
**Caveats:** global firehose (no server-side filter), no replay/history (subscription only sees post-subscribe entries), 1 Hz coalescing, potential drops under heavy logging, and it doubles as the user's log page (spammy progress lines pollute it).

## 3. Plugin settings as a data channel (`configurePlugin`)

- **Write:** mutation [`configurePlugin(plugin_id: ID!, input: Map!): Map!`](https://github.com/stashapp/stash/blob/v0.31.1/graphql/schema/schema.graphql) line 450 → [`internal/api/resolver_mutation_configure.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/resolver_mutation_configure.go) `SetPluginConfiguration` + immediate `c.Write()`.
- **Read:** `configuration { plugins(include: [ID!]) }` → [`internal/api/resolver_model_config.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/resolver_model_config.go), reading the live in-memory config ([`internal/manager/config/config.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/manager/config/config.go)) — **no read-after-write staleness via GraphQL**.
- **Officially sanctioned, not a hack**: the [Plugins doc](https://docs.stashapp.cc/in-app-manual/plugins/) states: *"Plugin settings can also be set using the graphql mutation `configurePlugin` — the settings set this way do not need to be specified in the `settings` field unless they are to be displayed in the stock plugin settings UI."*
- **Community-standard**: [`cs-ui-lib.js`](https://github.com/stashapp/CommunityScripts/blob/main/plugins/CommunityScriptsUILibrary/cs-ui-lib.js) (CommunityScripts UI library) implements exactly `getConfiguration` (`configuration { plugins }`) / `setConfiguration` (`configurePlugin`) via plain `fetch(baseURL + "graphql")`.
- **The Python task can write these itself**: the raw plugin's stdin envelope contains `server_connection` (scheme/host/port + session cookie) precisely so plugins can call GraphQL back ([Plugins.md — Plugin task input](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/docs/en/Manual/Plugins.md)).

**Caveats:** `SetPluginConfiguration` **replaces the whole map for that plugin** ("It will overwrite any existing configuration" — code comment), so read-modify-write is mandatory to preserve user settings; each call **rewrites stash's config.yml** (fine for a final result, wrong for per-scene progress); **no `configurationSubscribe` in v0.31.1** (only jobs/logging/scanComplete — schema lines 598–606), so the UI must poll to see task-written values; historical bug [#4740](https://github.com/stashapp/stash/issues/4740) (configurePlugin wiping *other* plugins' in-memory settings) was fixed by PR #4845 and the v0.31.1 code is per-plugin keyed.

## 4. Other mechanisms in v0.31.x

- **`runPluginOperation(plugin_id: ID!, args: Map): Any`** — the star finding. Added in v0.25.0 by [PR #4603](https://github.com/stashapp/stash/pull/4603) (*"run synchronous plugin operations with a return value, without using the task manager"* — [changelog](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/docs/en/Changelog/v0250.md)). Resolver → [`Cache.RunPlugin`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/plugin/plugins.go) spawns the plugin's `exec` (same raw stdin-JSON envelope, `args` map), waits for exit, and **returns the parsed stdout `output` field as the GraphQL response** (non-zero exit or `"error"` key becomes a GraphQL error). No job, no queue, blocks the HTTP request until done. Community usage: [Mosaic Poster](https://discourse.stashapp.cc/t/mosaic-poster/12358) frontend calls `runPluginOperation` from its UI JS. There is no generated hook in `PluginApi.GQL` (the stock UI doesn't use it), but plugin JS can call it via `csLib.callGQL`, plain `fetch` to `graphql`, or `PluginApi.libraries.Apollo` / `PluginApi.libs.StashService.getClient()` (both exposed — pluginApi.d.ts lines 613/818).
- **`interface: js` (embedded)**: runs a fresh [goja](https://github.com/dop251/goja) VM per task ([`pkg/plugin/js.go`](https://github.com/stashapp/stash/blob/v0.31.1/pkg/plugin/js.go)) — no Node APIs, no sockets, no long-lived process; APIs are `log.*` (incl. `log.Progress` → job progress) and `gql.Do` (sync GraphQL) ([Embedded plugins doc](https://docs.stashapp.cc/in-app-manual/plugins/embeddedplugins/)). Does not solve streaming.
- **`interface: rpc`**: JSON-RPC over stdio, still per-task process, still stdout-envelope output; Go-oriented.
- **No built-in plugin HTTP/WebSocket hosting in v0.31.x.** Escape hatch: `ui.csp.connect-src` in the plugin yml adds URLs to the page's Content-Security-Policy `connect-src` ([`internal/api/server.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/server.go), [Plugins.md csp field](https://github.com/stashapp/stash/blob/v0.31.1/ui/v2.5/src/docs/en/Manual/Plugins.md)), so a plugin may run its own sidecar HTTP/WS server and its UI JS may fetch it — viable but heavy (port management, lifecycle, auth).

## 5. The snapshot-assets approach — limitations confirmed

- Assets are served by [`routes_plugin.go`](https://github.com/stashapp/stash/blob/v0.31.1/internal/api/routes_plugin.go) via Go's `http.FileServer`: it honors `Last-Modified`/`If-Modified-Since` but **sets no `Cache-Control`**, so browsers apply heuristic caching to unchanged URLs — **stale snapshots** unless you cache-bust (query string with mtime/version) or `Cache-Control: no-cache` via a `middleware`… not configurable. Poll interval is entirely client-side.
- **Partial reads**: the handler streams the file directly from disk; a plugin writing in-place can be read mid-write. You must write to a temp file + atomic `rename` in the same dir.
- **Multiple tabs**: N independent pollers reading shared global state; races are benign (read-only) but last-writer-wins across concurrent tasks writing the same filename.
- It's an accepted community pattern (Mosaic Poster writes generated JPEGs into its plugin dir and serves them via `ui.assets`), just with no push and no completion signal.

# Recommendation

**(a) Short task results — "save mapping succeeded/failed with errors":** switch to **`runPluginOperation`**. Have the Python task exit with the stdout JSON envelope (`{"output": {...}}` or `{"error": "..."}`) and have the UI call the mutation and render the response (or GraphQL error) directly — one round-trip, no files, no polling, structured JSON. This is the exact feature it was built for (PR #4603) and is proven by Mosaic Poster. Fallback/complement: `loggingSubscribe` filtered on `[Plugin / <name>]` for error lines if you want them in a toast even when the page wasn't the caller.

**(b) Long-running progress — "phase 2/5, 8,412/20,595 scenes, current scene title":** use **both** of the first-class channels instead of the assets snapshot:
1. Emit `\x01p\x02<float>` stderr frames from Python for the numeric percent, and have the UI consume **`jobsSubscribe`** (+ `findJob` polling fallback) — copy Stash's own `useMonitorJob` pattern; you get a live throttled (100 ms) progress bar and a terminal FINISHED/FAILED event with zero polling loops.
2. Emit `\x01i\x02<text>` stderr frames for rich status lines ("phase 2/5 — 8,412/20,595 — <title>") and consume them via **`loggingSubscribe`**, filtering on the `[Plugin / <name>]` prefix. For a structured "current phase" that must survive page reloads, additionally checkpoint it (once per phase change only) via **`configurePlugin`** (read-modify-write!) and read it back from `configuration { plugins }` on mount — the officially documented settings side channel.

Retire the assets-dir JSON snapshot for control data (keep `ui.assets` only for genuinely static assets like images). If you later need sub-second structured streaming, the only v0.31.x-sanctioned path is a plugin-owned sidecar server whitelisted via `ui.csp.connect-src`.
